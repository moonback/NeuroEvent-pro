Problèmes de sécurité identifiés

Critique
Buckets Storage publics (signatures & photos)
Toute URL expose des documents contractuels confidentiels sans authentification. Risque RGPD immédiat. Solution : URLs signées à durée limitée via Supabase Storage.
Critique
Fallback user_metadata pour la résolution des rôles
Les données user_metadata sont modifiables côté client. Un attaquant peut s'auto-promouvoir administrateur. Résolution exclusive via la table profiles côté serveur obligatoire.
Critique
Politiques RLS configurées à true (accès total)
Absence de filtrage par user_id : un technicien peut lire toutes les missions. Chaque politique doit être filtrée par l'identité authentifiée.
Élevé
JWT stocké dans localStorage (exposition XSS)
Un script injecté peut exfiltrer le token de session. Migration vers des cookies HttpOnly + SameSite=Strict recommandée.
Élevé
Logique métier 100% client-side (conflits & stocks)
lib/conflicts.ts et lib/stock.ts s'exécutent dans le navigateur. Contournable via la console. Migration vers PostgreSQL Functions (RPC) indispensable pour garantir l'atomicité.
Élevé
Anti-pattern "meta:" dans required_skills
Violation de la 1NF : métadonnées hétérogènes (dates, URLs, rapports) sérialisées dans un tableau de strings. Rend le filtrage SQL impossible et expose à des crashs si une chaîne est corrompue.
Moyen
Absence de validation Zod sur les entrées
Aucune validation de schéma côté serveur n'est mentionnée. Zod doit couvrir tous les points d'entrée de données.

Dette technique & qualité du code

Critique
Store Zustand monolithique — 1 800 lignes
store/index.ts mélange état, logique métier et DAL. Risque élevé d'effets de bord. Refactoriser avec le pattern createSlice ou combine.
Élevé
Composants surdimensionnés
DrawerTabs.tsx (~1 200 lignes), MissionModal.tsx (~600 lignes), Settings.tsx (~700 lignes avec stats codées en dur). Découpage en composants atomiques urgent.
Élevé
Sous-composants déclarés à l'intérieur du parent
Dans DrawerTabs.tsx : les composants d'onglets sont re-instanciés à chaque re-render parent. Anti-pattern React critique sur mobile. Déplacer en dehors du composant parent.
Moyen
Duplications de logique
renderPhotoSection dupliqué entre onglets. formatDuration présent dans deux fichiers distincts. Extraire en hooks ou utilitaires partagés.
Critique
Zéro test automatisé
"Fear-driven development" : chaque modification du schéma est à haut risque. Mettre en place Vitest (unitaires) + Playwright (E2E) sur les flux critiques immédiatement.
Moyen
Statistiques codées en dur dans Settings.tsx
Nuit à la crédibilité du système en production. Ces valeurs doivent être calculées dynamiquement depuis la base de données.

Analyse des performances

Critique
fetchMissions() sans pagination — seuil de rupture à 500 missions
Récupère l'intégralité des données. Saturera la bande passante mobile dès 500 missions actives. Implémenter la pagination + filtrage par plage de dates côté serveur immédiatement.
Élevé
Absence de React.memo et mémoïsation
Re-renders en cascade sur les listes mobile. Ajouter React.memo, useMemo et useCallback sur les composants coûteux.
Élevé
Fuite potentielle de listeners Realtime
Lors des hot-reloads, les abonnements PostgreSQL ne sont pas nettoyés. Implémenter un cleanup rigoureux dans les useEffect.
Moyen
Debounce 400ms sur les changements PostgreSQL
Perceptible sous forte activité. Évaluer la réduction à 100-150ms ou un mécanisme d'invalidation ciblée.
Moyen
localStorage multi-onglets — risque de collision
Les clés eventflow_checklist_${"{userId}"}_{"{missionId}"} peuvent se désynchroniser en multi-onglets. Envisager IndexedDB avec BroadcastChannel ou Supabase Realtime pour le mode offline.

Plan d'action priorisé

Phase 0 — Sécurité critique (sprint 1-2, ~2 semaines)
Supprimer le fallback user_metadata — résolution des rôles via table profiles uniquement
Passer les buckets signatures & mission-photos en privé + URLs signées
Réécrire les politiques RLS avec filtrage par user_id
Ajouter validation Zod sur tous les points d'entrée
Phase 0 — Migration données (sprint 1-2, ~2 semaines)
Migrer les métadonnées meta: vers des colonnes SQL typées (delivery_date, pickup_date, setup_time…)
Déplacer lib/conflicts.ts et lib/stock.ts vers des PostgreSQL Functions (RPC)
Implémenter la pagination + filtrage serveur dans fetchMissions()
Phase 1 — Refactorisation & fiabilité (sprint 3-5, ~4 semaines)
Découper le store Zustand monolithique en slices fonctionnels
Extraire les composants atomiques (PhotoGrid, DurationDisplay, etc.)
Déplacer les sous-composants DrawerTabs hors du composant parent
Supprimer les statistiques codées en dur dans Settings.tsx
Mettre en place Vitest (unitaires) + Playwright (E2E) sur flux critiques
Migrer JWT vers cookies HttpOnly + SameSite=Strict
Phase 2 — Observabilité & DevOps (sprint 6-7, ~3 semaines)
Déployer Sentry pour le monitoring d'erreurs
Mettre en place une pipeline CI/CD avec vérification des types et tests
Ajouter React.memo et mémoïsation sur les composants coûteux
Nettoyer les listeners Realtime dans les useEffect
Phase 3 — Scalabilité (sprint 8+)
Implémenter le lazy loading des routes et composants lourds
Évaluer une stratégie de cache (React Query / SWR) pour remplacer Zustand + fetch manuels
Documenter l'architecture pour l'onboarding des nouveaux développeurs
